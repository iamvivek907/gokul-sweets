# Customer theme contract

## SCRUM-107 owner-approved arrival palette

The arrival screen and approved eight-item menu demo define the shared customer appearance when the effective customer visual flag is on: deep teal `#092725`, hero teal `#143936`, cream `#fffaf2`, coral action `#c76752`, readable ink `#172e2c`, and light bordered surfaces. `frontend/components/layout/customer-journey.css` applies these tokens within `.future-storefront` across menu, cart, checkout, orders, navigation and overlays. The server's effective flags still control the visual shell; the flag-OFF appearance is unchanged. Branch cards open the selected live menu. A cross-branch switch explicitly reviews the current cart and, only after confirmation, clears it, resets the selected pickup slot and opens the new branch menu. Placed orders are unaffected. A real paid `CONFIRMED` order alone receives the prominent confirmation tick.

Across customer pages, decorative text and action labels resist accidental selection; inputs, prices and order numbers remain copyable. The viewport fits narrow screens without page-wide horizontal movement, while intended carousels retain contained scrolling. Buttons use touch manipulation to avoid accidental double-tap zoom. The owner's subsequent request on 27 Sep explicitly opts for a fixed device-width mobile viewport without pinch zoom; the viewport declares `maximumScale: 1` and `userScalable: false`, and the customer shell allows panning while disallowing pointer pinch gestures. Browser or operating-system accessibility settings may override those controls. Layouts must still reflow with larger system text and desktop browser zoom.

The approved Sprint 2 customer visual direction lives in the shared customer shell. New customer stories inherit it automatically when they render inside `AppShell`; staff and admin screens keep their own design.

## Implementation rules

- Keep customer pages inside `frontend/components/layout/AppShell.tsx`. The shell owns the header, branch control, footer, mobile drawer and bottom navigation. Do not add a second customer header or mobile navigation in a page.
- Add visual rules to `frontend/components/layout/futuristic-storefront.css` under `.future-storefront`, or to a feature stylesheet scoped beneath that class. Reuse the existing ink, muted, gold and border variables and the shared focus and reduced-motion treatments. Keep flag-OFF presentation intact.
- Checkout's frame and navigation are in `frontend/components/checkout/checkout-experience.css`; keep it visually aligned with the shell. Preserve checkout's functional branch change and progress flow.
- `futuristicStorefrontV2` is the independent customer-wide visual switch; the effective `checkoutExperienceV2` also turns on the shared shell so checkout never mixes old navigation with the new frame. The backend publishes effective values via `/api/storefront/features`. Do not use a client-only flag or hardcode an always-on theme.
- Check desktop and narrow mobile for home, menu, product, cart, checkout, orders, profile and the drawer. Check keyboard focus, reduced motion, long branch names, and a cart with items before approving a new customer story.
- A deliberate rebrand should change this contract and shared components in one reviewed PR. Do not restyle a single story into a separate visual system.

The `frontend/tests/customerThemeContract.test.cjs` regression runs in GitHub Actions. It checks that the shell still owns both navigations, loads the scoped stylesheet, and uses the server's effective feature flags. Visual review is still necessary for new pages; a static check cannot prove every layout is consistent.

## Compact phone ordering

Below 641px, the enabled customer shell uses compact menu rows with product photography and 44px controls at right, shorter branch/checkout sections, horizontal add-on cards and a slim bottom action with its own content spacer. Desktop typography, gallery, grid, checkout and navigation stay unchanged. With `simplifiedCheckout`, `checkoutExperienceV2` and `acceptedCheckoutQuote` effective together, the phone menu Continue action opens `/checkout/mobile`. Cart edits, pickup selection, inline verified contact, the best eligible offer, price details and add-ons stay on one page, and Pay opens the configured gateway. With only simplified checkout effective, the direct pickup selector remains the fallback; desktop retains `/cart` and its existing steps. Enabled compact phone visits to `/cart` redirect to `/checkout/mobile`; desktop and flag-OFF cart presentation stays unchanged. Payment preparation and hosted redirect display a branded loading screen without flashing the reserved-order recovery card. The phone checkout provides Branch home, Back to menu, per-item removal, selected-item bulk removal and Clear cart; removing the final item returns to the menu automatically. Pickup changes use a compact, centred native dialog with the desktop date/time card styling, visible Close, outside-tap/Escape dismissal and explicit confirmation; cancelling preserves the previous pickup. Confirmation rechecks the selected date with the current cart on the server; unavailable slots or a failed check preserve the saved choice and leave the error in the dialog. Phone cart settings outages, including fresh offline visits without cached flags, offer an explicit recovery surface and retry without hiding the saved cart indefinitely. First-time phone verification still requires the provider’s OTP interaction. New pickup and delivery orders require verified owner sign-in by default (`GOKUL_CHECKOUT_GUEST_ENABLED=false`); browsing stays open. Identity outages preserve the cart and block unverified checkout rather than silently allowing guests.

A branded phone welcome lasts at most 2.4 seconds on document entry, with automatic G → brand → tagline animation and Escape dismissal, and does not restart for client navigation. A long app resume shows it again except during checkout or order detail/payment return. Direct payment returns and order details skip the welcome. It never waits for the API. The selected branch menu is prefetched once and consumed within 15 seconds; unused entries expire automatically; consumed in-flight requests retain their original 15-second deadline and deduplicate warmups until settlement; the cache and active warmups together hold at most three branches, and expired/evicted requests are aborted; the first eight product images and stored branch cover are warmed without blocking entry. Mobile paid returns show a branded verification loader until order navigation; Pending verification offers compact check/resume/cancel controls and keeps temporary failure, cooldown and paused-polling notices visible; deliberate navigation preserves the same stay, keep-order or provider-verified cancellation choices as desktop; failed/expired payments show compact recovery rather than the full desktop payment page. Compact mobile order history and detail reuse authoritative status, readiness notices, branch contact, pickup codes and reviews. Paid orders download a paginated PDF invoice from recorded item, tax, fee (including delivery), offer-savings and total amounts; unpaid orders never receive a paid invoice. Invoice PDFs embed English, Hindi and Tamil fonts, render selectable/searchable text, and expose document language, title, headings and paragraphs in logical reading order. Shaped Unicode text retains its original copying order. The PDF module and font files load only on download; a font failure shows a retryable error. Desktop order and payment layouts stay unchanged. Order detail retry opens that order’s payment recovery. Recovery reads its fulfillment type from the server and checks the provider before releasing reservations or starting a fresh checkout; a provider error preserves the existing order, and late capture follows refund reconciliation. Payment methods and native app handoff remain controlled by the configured provider.

Mobile portion choices are explicitly linked in Admin → Menu → Mobile portion choices. Group cards and quick-browse shortcuts retain the original SKU IDs, branch prices and stock; Half/Full prices are never inferred. Mobile category, maximum-price and portion-choice filters combine, without a diet filter. Desktop continues to show its original separate products. Customer-specific draft offers require a live phone-matched session, final total changes block gateway opening, and an interrupted order POST is recovered using its exact persisted request and idempotency key. Existing reservations are resumed rather than silently duplicated.

## Customer order numbers

A confirmed retail order receives a permanent short numeric label, shown as Order #1, #2 and so on across customer history/details/profile, invoices, staff queues/details/handover and kitchen tickets. The database sequence is shared across branches and never resets by date; rolled-back transactions can leave gaps. Existing confirmed/fulfilled orders are numbered during migration. Pending/failed orders retain their reference until confirmation. The original opaque reference continues to identify API routes, payment recovery, owner checks, mutations and saved histories. The public label is never an access credential. Staff may look up the short number across pages with ORDER_VIEW and existing branch authorization; pickup still requires the four-digit pickup code. Layouts and checkout/payment flows stay unchanged.
