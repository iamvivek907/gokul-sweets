# Compact mobile PWA installation

The install promotion is optional and follows the approved customer teal, cream and coral surfaces below 641px. The effective futuristicStorefrontV2 or checkoutExperienceV2 shell displays one compact card on Home, branch home and Profile. Profile copy mentions orders and rewards. There is no new header or bottom navigation, campaign overlay, checkout/payment/order prompt, or mandatory installation. Desktop and the flag-OFF legacy home retain their previous install presentation.

## Existing implementation audit and identity

- Next.js App Router, with the manifest generated by `frontend/app/manifest.ts` at `/manifest.webmanifest`.
- Existing canonical manifest `id: "/"`, `start_url: "/"`, `scope: "/"`, `display: "standalone"`. Name, short name, colours, orientation and existing 192/512/maskable icons are retained byte-for-byte. The application origin remains the deployed origin; DEV and production are distinct origins, not interchangeable installs.
- One existing `/sw.js` worker, registered at scope `/`. Customer/staff push registration calls target the same script and root scope. No second manifest, worker, registration scope or dependency is introduced.
- Existing versioned static/page/image caches use v2. Navigation is network-first with offline fallback; scripts/styles/fonts are stale-while-revalidate; images are cache-first. Non-GET requests and `/api/` requests bypass worker caching. App Router data fetches are not added to the cache rules.
- Existing automatic worker activation (`skipWaiting`, `clients.claim`) and no forced page reload are preserved. The worker script has no-cache headers. Future worker byte changes update the same registration; navigations request fresh pages and hashed build assets. An open page is not forcibly refreshed during OTP, order submission or payment. No fabricated “new version” banner is introduced when no worker version has changed.
- Existing analytics is an allowlisted web-vitals collector, not a generic product-event provider. Installation does not add a provider or send unsupported event types to this endpoint. All frequency metadata is local and contains no customer identity, phone or order data.
- Existing local/session cart, identity, pickup, order and recovery keys are untouched. The new `gokul-pwa-install-preferences-v1` key contains only installation UX preferences.

## Detection and Android flow

The existing `usePwaInstall` now subscribes to a document-wide external store. Root `PwaInstallRuntime` captures browser events even before an eligible banner mounts. All consumers share one deferred event, in-progress guard and installation state.

Standalone recognition includes `(display-mode: standalone)`, minimal-ui/fullscreen and iOS `navigator.standalone`. iOS identification includes touch-enabled iPad desktop user agents. The store does not inspect device-wide installed apps. Stored “installed” markers are ignored as evidence.

On Chromium, the banner only exposes Install App when `beforeinstallprompt` is available. Explicit clicks consume and clear that single-use event before invoking it, then await `userChoice` (or the prompt result for compatible implementations). Web Locks prevents simultaneous native prompts across tabs; persisted cooldown is rechecked inside the lock. Older unsupported browsers use the focused document and shared preference events. A rejection applies a cooldown; failure consumes the unusable event and displays a readable explanation that browsing still works. Acceptance hides promotion for this session without declaring device-wide installation. Actual `appinstalled` events clear promotion and are relayed to other live tabs using BroadcastChannel. No acceptance opens another modal.

## iPhone flow and accessibility

An explicit tap opens a branded native HTML dialog styled as a compact bottom sheet. It lists Share → Add to Home Screen → Add and suggests Safari if the option is missing. The guide does not imitate browser/system UI or claim that installation occurred. It has visible Close and Got it buttons, initial focus on Close, trapped dialog focus, Escape/outside dismissal, focus return, scrollable content and 44px controls. English/Hindi use the existing language system, retaining native menu names for recognition. Larger text, reduced motion and safe-area padding are supported.

An active CustomerIdentityPanel operation suppresses promotion through reference-counted store blockers. Other visible modal dialogs prevent an install action being stacked. Checkout, payment and order routes never display the new promotion.

## Frequency and failure handling

Local preferences contain `installBannerDismissedAt`, `installPromptLastShownAt`, `installPromptResult`, `installInteractionCount`, and bounded impression timing/counts. Closing the banner or rejecting the native prompt suppresses promotion for seven days. Native failure uses a one-day cooldown. Impressions are counted at most once a day; after three ignored visits, the next promotion is deferred for a week. Storage/focus/visibility events synchronize cooldowns. Blocked or malformed storage falls back to in-memory preferences and never prevents ordering.

Local storage is not installation proof. The current document's actual standalone/appinstalled signals hide promotion; another ordinary browser visit cannot universally determine whether the app is installed elsewhere.

## Validation and device QA

Automated coverage tests centralized capture, concurrent consumers/tabs, choice/rejection/acceptance, appinstalled races, failure, blocked storage, seven-day cooldown expiry, stale stored installation markers, iOS instructions, standalone modes, ignored-visit suppression and independent OTP blockers. Browser checks exercise real click activation through Web Locks, native-event consumption, cross-tab cooldown, 320/390/640px sheets, desktop at 641/1280px, theme OFF, Home/branch/Profile placement, safe routes, OTP suppression, focus/Escape/outside dismissal and screenshots. Existing ordering/account/rewards regressions and CI remain required.

Headless browser tests simulate browser installation signals; they cannot install or replace an operating-system app. Before a separately authorized deployment is signed off on phones, manually verify Android Chrome accept/reject/standalone launch, iPhone Safari Share/Add to Home Screen, QR navigation to the same origin, and an existing installed app receiving the deployed assets at its next load without duplicate identity. No deployment is performed by this implementation task, so live installed-device update verification remains device QA.
