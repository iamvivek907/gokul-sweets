# Menu and checkout performance investigation

The October 9 DEV logs show an idle menu repeatedly checking availability, then a one-item order taking 4.3 seconds and payment initialisation taking 4.8 seconds. The latter includes 3.6 seconds inside PhonePe token acquisition. Container samples rise to 491 MiB. These observations identify slow requests; they do not establish a safe production customer count or prove a memory leak.

## Changes

- Pickup previews now load service rules once per request, rather than once for item validation and again for slot evaluation. Manual/sold-out/dependency checks run first; the same request-local evaluator checks the dated slots. Later requests read fresh rules. Stock reads, reservation locking, pricing and checkout acceptance remain authoritative.
- Dated item summaries index the issues of open slots once. Previously each product repeatedly scanned the issue lists of every slot. Preserve request order, stock failures, first applicable reason, normal/priority capacity and pickup-window exclusions. The frontend also indexes the selected slot's issues.
- Full-menu previews opt into a response-local issue catalog (`menuPreview=true&compact=true`). Each distinct complete item issue is serialized once; slots reference it by index, retaining original order and duplicates. The frontend expands the original UI contract and accepts legacy responses during separate backend/frontend deployments. Cart requests and legacy menu clients keep their full response. This changes transport only, with no stock caching or evaluation shortcuts. A synthetic 100-item, 40-slot unavailable-stock response measured 861,036 bytes before and 58,417 bytes after (about 93% smaller, before HTTP compression); actual savings depend on repeated issues.
- Menu catalog and advisory availability caches use 64 bounded lock stripes for rebuild coordination. Database work no longer holds the global LRU lock. Valid cache hits also bypass rebuild coordination, so independent branch/revision reads can run concurrently even for the same branch. Cold misses still rebuild under the branch stripe and revalidate before publication. Branches sharing a stripe still coordinate; the LRU retains its existing limits. Revision checks, write-transaction cache bypass and the one-second/boundary advisory expiry remain intact.
- Notification bell and sound runtime share overlapping inbox requests. No settled private result is retained. Identity changes, including cross-tab invalidations, abort obsolete reads. Cancelling one subscriber preserves other subscribers; cancelling the last aborts the request. The bell reads the authenticated inbox directly rather than checking identity first. Guest/disabled polling pauses after 401/403/404, and retries on identity changes or visible app resumption. Sound settings and inbox reads run concurrently.
- Successful new orders log stage durations for identity, idempotency claim, validation, commitment preflight, pricing, slot reservation, persistence, ownership/rewards, inventory and linking. These timings exclude final response conversion and transaction commit. The HTTP/transaction metrics are still needed to attribute remaining end-to-end time.
- PhonePe logs token-refresh network duration separately from lock waiting. Its existing token cache/refresh lock is retained. The configured `PHONEPE_TOKEN_EXPIRY_SAFETY_SECONDS` now controls reuse; previously the client always used 30 seconds. The default remains 30. Additional diagnostic logging failures cannot replace checkout or verification outcomes.

Identical overlapping one-date compact previews now share an in-progress read, rather than each customer loading and evaluating the same batch independently. The key includes branch, date, item order, quantities, weights and the observed wall-clock second. Joining is restricted to the first 250 ms of a read; older reads, different requests and registry saturation perform fresh reads. At most 64 distinct reads are registered, with no database work or waiting under the registry lock. Entries are removed before publishing either a result or an exception. There is no settled-result cache: any request arriving after completion rechecks the database. Only the explicitly opted-in public menu preview uses this coordinator. Cart, checkout, legacy responses and multi-date availability retain independent reads. These overlapping requests share an advisory snapshot; stock/branch changes during an active read are not an ordering guarantee, and checkout remains authoritative.

## Verification and limits

The summary regression compares the indexed implementation with the previous algorithm over 400 seeded scenarios. A local CPU-only comparison of 100 items (the endpoint batch limit), 40 slots and 20 summaries measured about 42 ms for the original implementation and 10 ms for the indexed implementation. An exploratory 500-item helper comparison also improved, but it is not a single real API request: the browser splits menus into 100-item batches. Neither comparison predicts total customer latency or capacity.

Concurrency tests hold one branch rebuild while another completes, and verify that callers for the same branch share the rebuilt snapshot. Pickup validation tests verify one evaluator build for manual checks plus 40 slot evaluations, fresh loading on a later request, and rejection of sold-out products. PhonePe tests cover concurrent token reuse, the configured safety window and exact UTF-8 HMAC payload verification. Inbox tests cover overlapping reads, cancellation, account/read invalidation, guest polling pause/resume, hidden/offline tabs and unmounts.

The disposable localhost Docker workload exercises complete full-menu previews against both memory profiles. The existing 512 MiB Docker defaults must pass 100 concurrent complete previews; a separate 2 GiB / 1 CPU profile must pass 100 and 500. Both run mixed customer/staff and 31-day discovery workloads through 1,000 concurrent clients. The original required Docker check name is retained as a fail-closed aggregate over both profiles. The 512 MiB profile keeps the runner's CPU defaults, so it does not simulate Render's 0.1 CPU allocation or establish its capacity. Its earlier 500-client results are observations, not passing browser-deadline checks.

Each complete preview now has the browser's eight-second deadline spanning all four sequential POSTs for the 379-item fixture. Timeouts count as errors, fail the workload, cancel the active request and stop later batches. Reports include resource profile, completed counts, deadline misses, successful-only p95 and all-attempt timings. Timed-out attempts are never reported as successful completions. Synchronous parsing overruns also fail. This is a synchronized synthetic localhost burst, not a sustained payment/browser/network soak or a production capacity guarantee.

Before the compact transport addition, this workload recorded zero errors and p95 2.068 seconds for 100 complete previews, and 8.197 seconds for 500. After compact transport, the 512 MiB run recorded p95 2.027 / 7.977 seconds, a slowest preview of 8.046 seconds and container samples up to 511 MiB. Separate CI runners and synthetic data make these observations unsuitable for attributing a precise percentage latency improvement. The fixture has one full-day slot per date with approved future stock; it does not represent the attached log's large repeated unavailable-item matrix. Those original runs used a 30-second per-HTTP timeout without the whole-preview deadline and do not prove browsers complete successfully. Keep the browser deadline unchanged; measure complete previews and worst-case repeated issues before approving a capacity target.

The first stricter deadline run (commit b46f17dc, Actions 37895103267) passed the 512 MiB / runner-default CPU workload: 100 complete previews, p95 1.911 seconds, zero deadline misses. On the capped 2 GiB / 1 CPU profile, 100 completed at p95 6.177 seconds, but all 500 previews exceeded eight seconds. The required aggregate failed correctly. Compilation and functional tests passed; this was a failed capacity assertion, not a compilation error. The in-progress sharing change responds to this duplicated-work bottleneck; its new workload result must be verified before claiming the 500-preview target is met.

## Planned Render resource upgrade

Increasing the instance from 0.1 to 1 CPU and from 512 MiB to 2 GiB provides CPU allocation and memory headroom, but does not guarantee ten-times-faster requests. The Docker default fixes the heap at 192 MiB; upgrading the instance alone does not increase it. CI tests this separate candidate environment override for the planned 2 GiB / 1 CPU profile:

```text
JAVA_TOOL_OPTIONS=-Xms128m -Xmx768m -XX:+UseG1GC -XX:ReservedCodeCacheSize=96m -XX:MaxDirectMemorySize=64m -XX:+ExitOnOutOfMemoryError
```

The production Docker defaults remain suitable for the existing 512 MiB limit. Do not apply the larger heap to that limit. No Render service, plan, secrets or deployment configuration is changed by CI. The profile must pass its workload before reporting a result; even then mobile network delay, database latency, payment-provider latency and sustained concurrency still need real deployment measurements. The test PostgreSQL service is colocated and has no matching production resource/network cap.

## Disconnected availability responses

The subsequent log contains `HttpMessageNotWritableException` wrapping `AsyncRequestNotUsableException`, Tomcat `ClientAbortException` and `IOException: Broken pipe` while serializing availability slot issues. The response connection had closed before the server finished writing. This can follow customer navigation, changing pickup/quantity (which cancels obsolete requests), a network/proxy disconnect or the eight-second preview deadline. The stack trace alone cannot distinguish these triggers or establish the request duration.

Recognized disconnects during response serialization now use Spring's disconnected-client logging (one DEBUG line, stack at TRACE) and return without attempting a second JSON body on the unusable connection. Genuine serialization, database and upstream failures retain error handling. This reduces misleading error logs; it does not make a slow computation fast or recover a disconnected request. The computation and compact-transport changes address different portions of loading time. The compatibility layer also backfills `throwIfAborted` without replacing native methods, preserving cancellation on legacy browsers.

## PhonePe callback investigation

The attached payment log rejected a callback with `INVALID_PHONEPE_WEBHOOK_SIGNATURE`, then confirmed payment through the status-refresh path. This particular rejection occurs after the configured key ID matches; it is not a missing-header or wrong-key-ID error. The controller already verifies the exact raw request bytes before parsing JSON.

[PhonePe's current webhook documentation](https://developer.phonepe.com/payment-gateway/website-integration/standard-checkout/api-integration/api-reference/webhook) describes HMAC and SHA authentication as separate dashboard choices. This application uses HMAC. A genuine provider callback and deployment configuration are needed to establish the reported mismatch; local signing tests cannot certify provider interoperability or the deployed secret.

For the DEV webhook, verify that the dashboard environment, webhook ID and generated secret match `PHONEPE_WEBHOOK_CHECKSUM_KEY_ID` and `PHONEPE_WEBHOOK_CHECKSUM_SECRET`. Do not substitute API client secrets or SHA username/password credentials. Preserve the raw UTF-8 body through any proxy; never decode/reformat JSON before verification. New rejection diagnostics record only body length, signature length and whether the signature has the expected hexadecimal shape. They do not record secrets, signature contents, expected hashes or payment payloads. Keep verification enabled and confirm a genuine callback succeeds; replay it to check idempotency.

## Measure on the intended deployment

After deploying through the normal reviewed process, compare the same branch/catalog and request mix before and after. Use an isolated environment with production-equivalent resource limits and a sandbox/mock payment provider.

1. Leave visible menus open for a sustained run at 100, then 500 simulated visitors, with realistic staggered entry. Include all feature and notification settings. Also test a simultaneous-opening burst, hidden tabs and returning online.
2. Include 100-item batches, a larger multi-batch menu, several pickup slots, unavailable service windows, stock not ready and actual carts. Record p50/p95/p99, timeout/error rate and complete-preview latency.
3. Mix browsing with checkout, payment return/status refresh and authenticated staff traffic. Use the new stage logs to choose query optimisations; do not remove validation or locks to obtain shorter timings.
4. Collect Hikari active/pending/timeout metrics, query count/duration, CPU, GC and total container memory. The default pool is five connections, but deployment overrides must be checked. The reported 491 MiB sample leaves little headroom if the limit is 512 MiB.
5. Recheck last-item and last-slot races, idempotent retries, payment callbacks and inventory commitments. Verify that changing service rules/stock or closing a branch still prevents invalid checkout.

The menu's branch, service-boundary, offers, settings and dated-availability freshness intervals remain unchanged. This PR reduces work per refresh and notification requests; it does not remove all idle menu traffic or establish a customer capacity limit. A smaller selected-slot preview contract or revision-aware public read model can be evaluated after the measurements above, with strict cart/checkout checks retained.

## Growing-table and time-window follow-up

Pickup lookups already have a unique `(branch_id, slot_date, start_time, end_time)` index. Dated allocations already have a unique `(branch_product_id, service_date)` index. Policies have a unique branch-product key, and notification inbox/unread paths have environment/subject indexes. No duplicates are added to these paths.

V124 adds only the missing ordered read paths: `orders(branch_id, created_at DESC)`, `orders(branch_id, order_status, created_at DESC)` and `payments(order_id, id DESC)`. The first two match existing newest-first staff pages; the last supports their existing highest-payment-ID status semantics. Staff pages now perform one indexed lateral `LIMIT 1` status lookup per selected order and return only IDs/statuses instead of hydrating payment entities and repeatedly running correlated maxima over retry histories. Page order, exact totals, authorization, delivery mapping and payment transitions remain unchanged.

The indexes are built concurrently. V124 is explicitly nontransactional, while other migrations retain their transaction handling. Flyway uses PostgreSQL session-level migration locking to allow concurrent index builds. If a concurrent build is interrupted, PostgreSQL may leave an invalid index; the migration rejects an invalid named index rather than silently treating it as complete. An operator must inspect the interrupted index and failed Flyway entry before repair/retry. No automatic drop, data deletion or production migration is performed here. Indexes consume storage and add write maintenance, so more indexes are not automatically better.

Time-window evaluation uses a hash map scoped to one pickup timestamp. Equal immutable `(startsAt, endsAt, weekdays)` windows share their pure `contains` and `nextChange` calculations. Product sold-out flags, stock, dependency traversal and cycle/depth guards remain separately evaluated; nothing is shared across timestamps or requests. Regression coverage includes every weekday mask, overnight/all-day windows, exact boundaries and manual checks. The existing dependency/branch-closure integration suite remains required.

The disposable query-plan benchmark uses temporary tables containing 100,000 synthetic orders across 100 branches and 300,000 payment attempts. It captures `EXPLAIN (ANALYZE, BUFFERS)` before and after matching indexes/query changes, checks indexed unsorted page retrieval, checks latest-status result equivalence and reports index sizes. The tables roll back on completion and never change application rows/indexes. These database-only, warmed synthetic plans do not predict full page-load times. PostgreSQL CI validation and new complete-preview workload results must pass before reporting improvement.

Exact page totals still count matching orders, and deep offset pagination still does more work as offsets grow. Report aggregation, historical imports and sustained mixed checkout traffic need separate real-deployment measurements; these changes do not promise constant loading time for every screen as all tables grow.

## Follow-up: 512 MiB deployment and varied customer traffic

The owner's current target is **512 MiB**, not 2 GiB. Do not set a 768 MiB heap on this instance. The entrypoint preserves the tested 192 MiB Serial GC profile for 512 MiB, unknown and unlimited cgroups. A finite container limit between 2 and 16 GiB selects the 768 MiB G1 candidate. Explicit `JAVA_TOOL_OPTIONS` always wins, so remove a stale 768 MiB override before deploying to 512 MiB. CI exercises both automatic profiles rather than overriding the larger one. No Render plan or deployed environment is changed by this PR.

Cold menu entry starts an independent display-only catalog read alongside the live menu read (also while an in-progress launch warmup is being consumed). Names, prices and photos can render first. Every provisional item is marked unavailable with CHECKING; late catalogs cannot overwrite a completed live read. Aborted navigation rejects obsolete callbacks and stops the display read. A failed catalog does not fail the live menu. A failed live menu uses the existing retry UI. Selected-date/time previews and Add/checkout acceptance retain their fresh checks. Display-only prices are never an accepted checkout quote.

Product cards retain Next's responsive optimization and lazy loading with explicit size hints and quality 75. Warmup no longer downloads eight original-resolution images in addition to optimized variants. This intentionally avoids speculative image preloads until actual above-the-fold images can be identified across phone/desktop filters and portion groups. Measure Android image transfer and LCP before adding eager/preload hints.

The existing 10% anonymous browser sample now accepts bounded MENU_NETWORK (request to headers, including server waiting), MENU_BODY (body transfer plus JSON parsing), MENU_PREVIEW (complete selected-date preview), MENU_RENDER (catalog state update to a subsequent paint opportunity), and MENU_IMAGE (resource duration). At most 12 values per stage are sent per mounted shell; no URL, branch/order ID, phone, cart or payload is included. Resource timing is not decoded-image paint time and may be limited by cross-origin timing permissions. MENU_NETWORK cannot by itself isolate database waiting; correlate it with server metrics. Rendering timers exclude time before the catalog receipt, and there is no per-customer trace correlation.

Internal Micrometer HTTP and Hikari acquisition timers record p50/p95/p99. Existing diagnostics log pool active/pending/max, latency samples, cumulative GC count/time and memory. Public actuator exposure remains health/info. Keep `GOKUL_METHOD_TIMING_LOG_LEVEL=INFO` and the existing slow threshold; all-method DEBUG/TRACE is not enabled. Disable `GOKUL_MEMORY_DIAGNOSTICS_ENABLED` after investigation if periodic logs are no longer needed.

Customer account history already uses the owner-scoped `(created_at,id)` seek query. The profile now appends those cursor pages with Load more, preserves existing rows on errors and deduplicates overlapping references. No exact count query is introduced. Administrative exact-total pages retain their existing contracts; changing them requires separate staff UI work.

Imports already support separately deployed single-job workers with `FOR UPDATE SKIP LOCKED` claims. Scheduling is explicitly bounded to one job at a time per process. Keep combined deployment defaults until a dedicated worker is healthy: then web can use `GOKUL_IMPORTS_ASYNC_ENABLED=true`, `GOKUL_JOBS_WORKER_ENABLED=false`; the dedicated worker uses `GOKUL_JOBS_WORKER_ENABLED=true`. Review each job's existing background flag before moving cleanup or reconciliation; disabling financial reconciliation on every process is unsafe. This change does not provision a worker or make synchronous exports asynchronous.

The workload adds unique full-menu quantities across seven dates, plus different cart subsets/quantities using the authoritative endpoint. Reports add p99 and pool size. The existing identical-preview capacity gates are preserved. Varied-preview deadline misses are explicitly reported as failed completions in an exploratory capacity observation; they do not establish or gate a previously unvalidated 100-user target. Unexpected HTTP/response errors still fail CI. The fixture has one slot per date and unit products; weighted products, many service windows, real Android networks and sustained payment traffic still require DEV testing.

Manual Build and verify runs accept database pool sizes 3, 5 and 8. Repeat the same branch/profile/traffic for each and compare throughput, endpoint p95/p99, acquisition waiting, pending connections, heap and GC. Default remains 5 connections / 24 HTTP threads. CI's 512 MiB runner CPU is not Render's CPU allocation; results do not prove Render capacity. No additional database indexes are added without query evidence.

Local follow-up validation: production frontend build, lint/type checks, Node regressions, 9 Python workload/startup tests, 8 CI-selection tests, backend compilation, Java formatting, 2,084-method documentation/timing coverage and targeted storefront-metric tests pass. Browser checks cover cursor-history recovery/reorder on 320/390/1280 px and legacy flags, early catalog rendering with live ordering blocked on 320/390/640/1024 px, quantities/weighted products/portion sizes/stock, and populated/empty/failed menu recovery on 320/390/640 px. Full PostgreSQL/backend suites, actual cgroup Docker startup and varied load measurements still require CI; no new Render capacity result is claimed.

## PR #201 review follow-up: preview deadlines

Shared one-date compact previews now wait interruptibly for at most five seconds from the owner's start. A joining request receives only the remaining budget. Timeout or interruption returns HTTP 503 with a retry message and does not cancel the shared owner or other followers. Interrupted threads retain their interrupt flag; completed stock results are still never cached.

Both owners and independent fallback previews use a separate read-only transaction with a five-second Spring timeout and PostgreSQL `SET LOCAL statement_timeout='5s'`. This caps SQL execution/lock waiting; the local setting disappears on commit or rollback. Checkout and full cart validation continue through their existing authoritative service. This does not add worker threads or change menu layout, heap settings, or database-pool sizing. These are database/wait deadlines, not a hard end-to-end request deadline: connection acquisition still uses Hikari's existing configured timeout (30 seconds by default), and transaction timeouts do not interrupt arbitrary Java computation.

Regression coverage includes follower timeout, interruption, remaining-budget handling, owner survival, original error propagation, fresh retry, fallback sharing behavior and transaction rollback. The PostgreSQL integration regression uses `pg_sleep`, confirms JDBC and Hibernate share the same connection, checks cancellation and local-setting reset, then retries through the coordinator. PostgreSQL integration execution requires the CI database.

Follow-up local checks pass: 23 targeted backend tests, Java formatting, documentation/timing coverage for 2,085 methods and 10 workload/JVM tests. The earlier PR CI passed backend and browser suites but stopped before Docker workload execution because the JVM fixture relied on runner cgroup paths. That fixture now uses controlled files for cgroup v1/v2, absent limits and operator overrides; runtime sizing behavior is unchanged.
